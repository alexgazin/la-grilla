# R7 MIDI behavior and acceptance

Core MIDI selects stable endpoint unique IDs saved per project. USB class-compliant devices and Apple's Bluetooth MIDI picker supply sources/destinations. Inputs can filter one channel or accept all and target any project instrument. Drums use the documented General MIDI map. Velocity-zero NoteOn is NoteOff; CC64 is sustain; channel-mode controllers are reserved. Learn maps a source/channel/CC to track gain/pan, master gain, filter or delay, with no incoming-note echo.

Input callbacks copy bounded packets into a preallocated multi-producer queue. The audio thread parses running status, split messages, SysEx/realtime and channel filtering, schedules host timestamps against audio samples and counts late events. Source-generation handles reject stale callbacks. Disconnect/overflow quarantines the source and releases its notes/sustain. Finite performance takes capture input note gates, sustain and per-source clear events; replay and WAV use the same DSP.

Output is generated by the audio clock into a bounded queue and sent by a separate serial Core MIDI worker. Harmony uses channel 1, bass 2, drums 10 and melody tracks 3–8. Note-offs precede same-time note-ons. Destination generations prevent old queued events from reaching a newly chosen endpoint. Panic, output errors, disconnect and suspension flush/release notes. The local mixer/FX shape app audio; external instruments determine their own volume, sound and effects. Performance MIDI exports additionally contain controller intent, without claiming identical external audio.

iOS requires the `audio` background mode to create virtual Core MIDI ports. The app continues explicit playback, but disconnects MIDI inputs, synchronously releases output notes and stops the output worker when its stopped graph enters the background. Permission text explains the Bluetooth picker. MIDI ports alone are not a silent background keep-alive.

Automated evidence:

- 62 Swift domain tests include settings/mapping validation, track deletion, recursive source migration and finite MIDI-input take projection.
- Six C++ suites cover the kernel, performance controls/effects, bounded MIDI parsing/generation, actual sample timestamps/sustain/source clear, finite PCM replay, output channel/gate timestamps, no input feedback, destination epochs and Panic.
- Both iOS SDK builds compile actual Core MIDI, AVAudioEngine and CoreAudioKit adapters.
- The native QA flow creates a real Core MIDI virtual source and destination, sends NoteOn/CC74/NoteOff through the actual callback/parser, learns CC74 and counts actual received output notes at that destination. This fixture exists only under `--uitesting`; it is not a simulated success label or production virtual keyboard.

Native acceptance and screenshot source/run identifiers are recorded in the stage screenshot README and [QA](QA.md) when complete. Simulator endpoints prove software routing, not physical USB/BLE compatibility. Before release, test wired and BLE controllers, channel filtering, sustain, hot unplug, reconnect, overload/Panic and actual note timing/DAW imports on the installed signed candidate. Bluetooth audio latency is separate from Bluetooth MIDI transport latency and must be measured separately.
