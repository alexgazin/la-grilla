# Первое воспроизведение переносимого проекта

При импорте `.grillapack` создаётся отдельный ID проекта. Его первое воспроизведение начинает с первого раздела и зацикливает **всю проверенную аранжировку**, включая следующие секции. Восьми- и шестнадцатитактовый проект не должен незаметно звучать только первыми четырьмя тактами.

Это локальная настройка транспорта: число тактов и включённый Loop хранятся в UserDefaults для нового ID, отдельно от музыкального документа. Схема проекта и формат архива не меняются. Сам архив, ноты, исходные записи, секции и настройки исходного проекта сохраняются. Настройки уже существующих ID не переопределяются.

При повторном открытии в том же хранилище настройка восстанавливается. Длина ограничивается оставшейся частью аранжировки от выбранной секции, а не длиной одной секции. Дальнейшие выбор секции, изменение длины Loop и выключение Loop — явные действия пользователя. Экспорт MIDI/WAV/stems по-прежнему использует диапазон, выбранный на экране Export.

Реализация: `Session.initializeImportedListeningPreference`, `restoreGeneratedLoop`, production `Session.importProject`. Новая настройка записывается после успешной установки для нового ID, включая случай, когда параллельная правка оставляет эту копию сохранённой, но пока не открытой. Проверка исходного ID/revision по-прежнему обязательна перед активацией; свежая работа не заменяется.

## Регрессия и проверка

Предыдущий код присваивал переносимой копии новый ID без настройки транспорта. Из исходного контекста в четыре такта импорт наследовал `loopBars = 4`; даже при отдельной настройке в 8/16 тактов восстановление ограничивало её длиной первой секции. Это установленный по коду дефект. Отдельный запуск старого бинарника с новым тестом не выполнялся.

Подготовлен `FirstResultTests/testPortableMultisectionImportPlaysWholeArrangementAfterFreshRelaunch`, с неизменным лимитом 120 секунд:

1. Настоящий локальный composer создаёт музыкальные fixtures в 8 и 16 тактов; каждая содержит две секции, первая — четыре такта.
2. Fixture кодируется настоящим portable encoder, записывается в файл и проходит production `Session.importProject`. Результат не подставляется в Session.
3. Проверяются новый ID, неизменность исходного архива/музыки/предпочтений, полный диапазон Loop и сохранённые музыкальные события.
4. XCTest завершает процесс и открывает то же реальное хранилище заново. Проверяются тот же ID и полный диапазон 8/16 тактов.
5. После настоящего Play фактический DSP tick должен пройти границу четвёртого такта при работающем движке, принятом generation и ненулевом выходном meter. Это программное наблюдение рендера, не измерение слышимого выхода физического iPhone.

Путь QA включён только одновременно с `--uitesting`, `--project-change-probe` и `--portable-import-bars 8` или `16`. Native-результат остаётся **Pending** до фактического завершения соответствующего exact-source запуска; подготовленный тест не считается PASS. Системный Files picker и внешние File Providers этой проверкой не принимаются.

Текст экрана Voice отдельно уточнён: музыка играет во время захвата, но подготовка и завершение работы микрофона могут кратковременно прерывать воспроизведение. Непрерывность обычных переходов между экранами и эти I/O-переходы имеют разные критерии приёмки; zero-gap захват не обещается.
